# Mini NPU Simulator 기능 명세

이 문서는 프로그램의 입력, 출력, 오류 처리와 완료 조건을 정의한다.
클래스, 함수, 모듈 구성은 `architecture.md`에서 정의한다.
요구사항의 기준은 `mission.md`이며, 아래의 비교·측정 기준은 미션의 권장사항을 채택한 구현 정책이다.

## 실행 환경 및 시작

- Python 3.8 이상에서 실행할 수 있도록 구현하며, 개발 기준 버전은 Python 3.11이다.
- Python 3.8과 3.11에서 세 모드의 정상 실행과 대표 오류 복구를 확인한다.
- `json`, `time` 등 표준 라이브러리만 사용한다.
- 저장소 루트의 `main.py`를 실행하면 다음 모드를 선택할 수 있다.
  - 모드 1: 사용자 입력 분석 (3×3)
  - 모드 2: `data/data.json` 분석
  - 모드 3: 지정한 크기의 Cross/X 생성 및 성능 비교
- JSON 파일 경로는 `main.py`가 있는 저장소 루트를 기준으로 해석하며, 현재 작업 디렉터리에 의존하지 않는다.
- 잘못된 메뉴 입력에는 안내 문구를 출력하고 다시 선택하도록 한다.
- 각 모드가 결과를 출력하면 모드 선택 화면을 다시 표시한다. 메뉴에서 `0`을 입력하면 프로그램을 종료한다.
- JSON 파일을 분석할 수 없을 때도 모드 선택 화면으로 돌아간다.

## 공통 기능 및 정책

### 데이터 저장 및 검증

- N×N 크기의 2차원 패턴과 필터를 저장하고 특정 위치의 값을 읽고 쓸 수 있다.
- 최소 3×3, 5×5, 13×13, 25×25 크기를 처리한다.
- 정수와 실수를 처리하며, 원소를 0과 1로 제한하지 않는다.
- 행렬 원소는 유한한 숫자여야 한다. JSON의 bool과 숫자가 아닌 값, NaN, 양·음의 무한대는 거부한다.
- 선언된 크기 N, 실제 행 수, 각 행의 열 수가 일치하는지 검증한다.
- MAC 연산 전에 패턴과 필터의 크기가 같은지 확인한다.
- 배열의 크기·숫자 여부 검증과 `expected`를 이용한 정답 비교를 구분한다.
  수동 입력 패턴이 실제로 십자가나 X 모양인지 확인하는 기능은 요구하지 않는다.

### MAC 연산

- 패턴과 필터의 같은 위치에 있는 원소를 곱하고 모두 더해 점수를 계산한다.
- NumPy 등 외부 라이브러리 없이 반복문으로 직접 구현한다.
- 점수는 실수일 수 있다.
- 패턴 하나와 필터 하나의 MAC 호출에 대한 연산 횟수는 N²이다.
  두 필터와 비교하는 한 케이스의 MAC 횟수는 2N²이며, 반복 측정 횟수와 구분한다.

### 점수 비교

- 미션에서 예로 든 절대 허용오차 `epsilon = 1e-9`를 사용한다. `abs(score_a - score_b) < epsilon`이면 동점이다.
  차이가 `epsilon` 이상이면 큰 점수를 선택한다. 차이가 정확히 경곗값인 `0.0`과 `1e-9`를 비교해도 두 번째 점수가 이긴다.
- 모드 1은 A/B/판정 불가, 모드 2는 Cross/X/UNDECIDED로 출력한다.
- 패턴 판정과 테스트의 PASS/FAIL은 별개다.
  JSON 모드에서 UNDECIDED는 정상적인 판정 결과지만, expected가 Cross/X이면 FAIL이다.

십진수 0.1은 이진수로 쓰면 무한히 반복되어 `float`에는 가장 가까운 근삿값이 저장된다. 덧셈 결과도 매번 표현 가능한 값으로 반올림된다.
제공 파일의 `size_5_1`에서 Cross 점수는 `0.9`, 0.1을 아홉 번 더한 X 점수는 `0.8999999999999999`다. 정확한 십진 합은 둘 다 0.9인데도 계산된 차이는 약 `1.11e-16`이다. [Python의 부동소수점 설명](https://docs.python.org/ko/3.11/tutorial/floatingpoint.html)

현재 6건 중 정확한 동점 3건에서 관찰한 차이는 최대 약 `2.66e-15`이고, 승자가 있는 3건의 최소 차이는 `8.8`이다. `1e-9`는 이 데이터에서 세 동점을 복원하면서 세 승자를 보존한다.
절대 허용오차를 고정하면 실제 차이도 `1e-9` 미만이면 동점 처리한다. 점수 규모나 누적 항 수가 크게 달라지면 반올림 오차가 이 기준을 넘을 수도 있다.

## 모드 1: 사용자 입력 분석

### 입력 및 오류 처리

- 필터 A와 B를 각각 3줄로 입력받는다. 각 줄은 공백으로 구분한 숫자 3개다.
- 각 입력 블록은 세 번째 줄에서 끝나며, 별도의 종료용 빈 줄은 입력하지 않는다.
- 두 필터의 저장 완료를 안내한 뒤 같은 방식으로 3×3 패턴을 입력받는다.
- 입력 도중 빈 줄은 행 부족 오류로 처리한다. 빈 줄, 열 개수 불일치 또는 숫자 변환 실패 시
  오류를 안내하고 현재 입력 중인 필터 또는 패턴의 3×3 전체를 다시 받는다.
  예: `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.`
- 이미 정상 저장한 다른 필터는 유지한다. A 오류는 A만, B 오류는 B만,
  패턴 오류는 패턴만 다시 입력받으며 모드 선택 화면으로 돌아가지 않는다.
- A/B는 사용자가 입력한 필터의 식별자다. Cross/X와의 대응 관계를 가정하지 않는다.
- expected 입력은 요구하지 않으며, PASS/FAIL 비교는 수행하지 않는다.
- MAC 결과가 유한하지 않으면 연산 오류를 안내하고 패턴 전체를 다시 입력받는다. 정상 저장한 두 필터는 유지한다.

### 처리 및 출력

1. 입력된 패턴과 각 필터의 MAC 점수를 계산한다.
2. epsilon 정책에 따라 A/B/판정 불가를 출력한다.
3. 3×3 성능 분석을 수행하고 평균 연산 시간과 N²를 출력한다.

결과에는 A 점수, B 점수, 판정, 3×3 평균 연산 시간(ms), 연산 횟수가 포함된다.

## 모드 2: JSON 데이터 분석

### 로드 및 스키마 검증

- `data/data.json`에서 `filters`와 `patterns`를 읽는다.
- 최상위 `meta` 등 검증 대상이 아닌 부가 정보는 분석에 사용하지 않고 무시한다.
- `filters`에는 `size_5`, `size_13`, `size_25`가 있으며,
  각 크기에는 `cross`, `x` 필터가 있다.
- `patterns`의 각 항목은 `size_{N}_{idx}` 형태의 키와 `input`, `expected`를 가진다.
- 패턴 키에서 N을 추출하고 `filters.size_N`의 두 필터를 선택한다.
- 필수 키, 키 형식, 숫자 배열, N과 배열 크기, 패턴과 필터의 크기를 검증한다.
- 파일이 없으면 오류와 파일 경로를 출력하고 처음의 모드 선택 화면으로 돌아간다.
- 파일 읽기 실패, JSON 문법 오류, 최상위 값이 객체가 아닌 경우,
  `patterns` 누락 또는 딕셔너리가 아닌 경우도 원인을 안내하고 모드 선택 화면으로 돌아간다.
  이 경우 케이스 분석·성능 측정·테스트 집계는 진행하지 않는다.
- 케이스 목록은 유효하지만 `filters`가 없거나 잘못된 경우에는 각 케이스를 필터 오류 FAIL로 기록한다.
- 케이스 단위 스키마·크기·라벨 오류는 해당 케이스를 FAIL로 기록하고 다음 케이스를 처리한다.
- 특정 크기의 필터가 없거나 잘못된 경우에는 해당 필터가 필요한 케이스를 FAIL로 기록하고,
  다른 크기의 케이스는 계속 처리한다.

### 라벨 정규화

| 입력 위치 | 원본 값 | 내부 표준 라벨 |
| --- | --- | --- |
| expected | `+` | `Cross` |
| expected | `x` | `X` |
| filter 키 | `cross` | `Cross` |
| filter 키 | `x` | `X` |

- 콘솔 출력과 expected 비교에는 표준 라벨 Cross/X를 사용한다.
- 지원하지 않는 라벨은 임의로 변환하지 않고 해당 케이스의 실패 사유로 기록한다.
- expected가 누락되거나 지원하지 않는 라벨이면 해당 케이스를 한 번만 FAIL로 집계하고 ID와 사유를 출력한다.
  입력 배열과 필터가 정상이어도 이 케이스의 점수 계산과 성능 측정은 수행하지 않는다.

### 케이스별 분석 및 출력

- 키·배열·필터·expected 라벨 검증을 통과한 각 케이스에 대해 두 필터의 MAC 점수를 계산하고 Cross/X/UNDECIDED로 판정한다.
- 판정이 정규화된 expected와 같으면 PASS, 다르면 FAIL이다.
- 케이스 ID, Cross 점수, X 점수, 판정, expected, PASS/FAIL을 출력한다.
- 검증 실패로 연산할 수 없는 케이스는 점수 대신 검증 실패 사유를 출력한다.
- FAIL에는 크기 불일치, 라벨 오류, 동점, expected 불일치 등 구체적인 사유를 남긴다.
- MAC 결과가 유한하지 않은 케이스는 계산 오류 FAIL로 한 번만 집계하고 사유를 출력하며, 성능 측정에서 제외한다.

### 성능 분석 및 최종 요약

1. 케이스별 결과를 출력한다.
2. 기본 3×3, 5×5, 13×13, 25×25 성능 분석 표를 출력한다.
   JSON에 유효한 다른 크기의 측정 조합이 있으면 해당 크기의 행도 추가한다.
3. 전체 테스트 수, 통과 수, 실패 수를 출력한다.
4. 실패 케이스의 ID와 사유를 목록으로 출력한다.

- JSON에 없는 3×3은 별도로 준비한 고정 측정용 배열을 사용한다.
- 검증 오류로 FAIL 처리된 케이스도 전체 테스트 수와 실패 수에 포함한다.
- 전체 테스트 수는 통과 수와 실패 수의 합과 일치해야 한다.

### 현재 제공 데이터의 검증 기준

- 현재 `data/data.json`은 총 6건이며, 위 epsilon 정책을 적용하면 통과 3건, 실패 3건이다.
- 실패 케이스는 `size_5_1`, `size_13_2`, `size_25_1`이며 모두 동점에 따른 UNDECIDED다.
  입력 십진수를 정확한 유리수로 계산하면 두 필터 점수는 각각 `9/10`, `15/2`, `49/10`으로 같다.
  따라서 이 세 건의 동점 자체는 부동소수점 오차가 만든 결과가 아니며,
  실제 float 계산에서 나타나는 미세한 점수 차이는 epsilon으로 동점 처리한다.
- 이 수치와 ID는 현재 제공 파일의 검증 기준이다. 데이터를 변경하면 실행 결과로 다시 집계하며,
  케이스 ID나 PASS/FAIL 개수를 프로그램에 하드코딩하지 않는다.

## 성능 분석 기준

- 패턴 하나와 필터 하나를 하나의 측정 조합으로 보고, 각 조합의 MAC을 R회 반복 측정한다. R은 10 이상이다.
- 모드 1은 입력 패턴과 A/B 두 필터의 조합을 모두 측정한다.
- JSON 모드의 유효 패턴은 키·배열·필터·expected 라벨 검증을 통과한 케이스다.
  모든 유효 패턴을 해당 크기의 Cross/X 두 필터와 각각 측정한다.
  정상 라벨의 expected와 판정이 불일치하거나 동점으로 FAIL이어도 측정에 포함한다.
  MAC 결과가 유한하지 않은 계산 오류 케이스는 측정에서 제외한다.
- 각 조합의 패턴과 필터를 행 순서대로 펼치고 두 구현의 점수가 같은지 확인한다. 2차원 MAC과 1차원 MAC을 각각 R회 연속 호출하고 각 구간 시간을 R로 나눈다. 배열 변환과 점수 일치 확인은 타이머 시작 전에 끝낸다.
- 입력, 출력, 파일 읽기, 라벨 정규화, 검증, 점수 비교 시간은 측정에서 제외한다.
- 크기별 모든 조합의 측정 시간 합을 총 MAC 호출 수로 나누어 평균 ms를 계산한다.
  유효 패턴이 P개이고 각 조합의 반복 횟수가 R이면 방식별 호출 수는 `P × 2 × R`이다.
- 표에는 크기, 방식별 호출당 평균 시간(ms), 배속(2D 평균 / 1D 평균), 호출당 MAC 횟수(N²), 방식별 호출 수와 데이터 출처를 표시한다.
- 같은 크기에 정상 케이스와 검증 오류 케이스가 섞여 있으면 정상 조합만 측정한다.
- 필수 네 크기 중 유효한 측정 조합이 하나도 없는 크기는 별도의 유효한 측정용 배열과
  두 필터를 사용하고 대체 데이터 사용 사실을 표시한다.
  오류 케이스의 데이터로 측정하거나 시간 0을 정상 결과로 출력하지 않는다.
- JSON 모드의 3×3 대체 데이터는 모드 3과 같은 생성기로 준비한다.
- 두 필터는 같은 크기라 호출당 MAC 횟수는 같지만 실제 측정 시간이 같다고 가정하지 않는다.
  두 필터 전체의 합산 시간을 호출당 평균 시간으로 표시하지 않는다.

### CPU 측정과 NPU의 병렬 MAC

성능 표의 배속은 같은 CPU에서 실행한 CPython의 2차원·1차원 반복문을 비교한 값이다. 두 구현은 원소를 순서대로 읽어 하나의 합계에 누적한다.
따라서 측정 시간에는 곱셈·덧셈뿐 아니라 인터프리터가 반복문을 실행하고 리스트에서 원소를 읽는 비용도 들어간다. 실제 NPU의 실행 시간은 측정 범위 밖이다.

일반 CPU에서도 SIMD 명령 하나로 여러 원소를 곱하거나 여러 코어가 입력을 나눠 부분합을 구할 수 있다. 부분합을 하나로 합치는 단계와 스레드 분할·동기화에는 비용이 들고,
메모리가 데이터를 공급하는 속도도 처리량을 제한한다. 작은 입력에서는 일을 나누는 시간이 절약되는 계산 시간보다 클 수 있다. [Intel의 SIMD·스레드 병렬화 설명](https://www.intel.com/content/www/us/en/developer/articles/training/explicit-vector-programming-best-known-methods.html)

NPU의 한 사례인 Google 1세대 TPU는 8비트 MAC 연산기 65,536개를 배열로 배치했다. 행렬을 작은 블록(타일)으로 나눠 병렬 처리하고, 칩에 올린 가중치를 여러 입력에 재사용해 외부 메모리 접근을 줄인다.
이 과제처럼 작은 패턴 하나에 필터 두 개만 적용하면 연산기를 충분히 채우기 어렵다. 입력 전송 시간과 가중치를 읽는 메모리 대역폭도 실제 처리량에 영향을 준다. [Google의 1세대 TPU 성능 분석](https://research.google/pubs/in-datacenter-performance-analysis-of-a-tensor-processing-unit/)

### 대규모 입력 분석

N=1000이면 한 패턴과 한 필터의 점수에 MAC 100만 회가 필요하다. 필터 두 개와 조합당 10회 반복을 쓰면 측정 구간에서만 방식별 MAC 2,000만 회를 수행한다. N을 2000으로 늘리면 위치 수와 행렬 저장량은 네 배가 된다. 같은 처리율을 가정한 시간 추정식은 `T(N) ≈ T(1000) × (N / 1000)²`이며, 캐시와 메모리 대역폭에 따라 실제 시간은 달라진다.

- **시간 실측.** Linux x86_64, Ryzen 7 5700G, CPython 3.11.13에서 생성기의 Cross 패턴 하나와 Cross/X 필터 두 개로 `benchmark_mac_layouts(..., repeats=10)`를 실행했다. 2D는 호출당 **44.54ms**, 1D는 **27.75ms**였다(방식별 20회). 이 조건에서 한 패턴의 두 점수를 2D로 한 번씩 계산하는 데 드는 MAC 시간은 약 89ms로 추정된다. 생성·검증·평탄화 시간은 별도다. 이 실험에서는 Python 함수에 N=1000을 직접 전달했다. 대화형 메뉴 3의 입력 범위는 1~512다.
- **메모리.** 8바이트 실수 100만 개를 연속으로 저장하면 행렬당 7.63MiB, 패턴과 필터 두 개에는 22.89MiB가 필요하다. 이 프로그램의 CPython 리스트는 원소 참조, 행별 리스트, 실수 객체도 보관한다. 측정용으로 패턴과 필터 한 쌍을 펼칠 때만 참조 슬롯 200만 개가 추가된다(64비트에서 약 15.26MiB, 리스트의 여유 용량 제외). 위 생성 데이터 실험의 프로세스 최대 상주 메모리는 약 **58.9MiB**였다(Linux `/proc/self/status`의 `VmHWM`). 생성 데이터에서는 0.0과 1.0 객체를 공유하므로 임의의 실수로 채운 JSON을 읽을 때의 메모리는 별도로 측정해야 한다.
- **최적화 순서.** ① 실제 입력에서 로딩·검증·변환·MAC 시간을 나눠 재고 최대 메모리를 함께 기록한다. ② 같은 필터나 패턴을 반복해서 쓴다면 평탄화한 배열을 한 번 만들어 재사용하고 변환을 포함한 전체 시간을 다시 비교한다. ③ 메모리가 먼저 부족해지면 표준 라이브러리의 `array('d')`로 행렬을 저장하거나, 입력 형식을 조정해 행·케이스 단위로 읽고 계산을 마친 버퍼를 해제한다. 현재 JSON 모드는 파일 전체를 읽으므로 MAC 반복문만 바꿔서는 로딩 시 최대 메모리가 줄지 않는다.

저장소 루트에서 실행한다. 모델을 만든 뒤 생성 원본 배열의 참조를 해제하고, Cross 패턴 하나를 두 필터와 각각 10회 측정한다.

```bash
uv run --no-project --python 3.11 python -B - <<'PY'
import platform
from pathlib import Path

from src.calculator import benchmark_mac_layouts
from src.models import Filter, Pattern
from src.patterns import generate_patterns

n, repeats = 1000, 10
cross, x = generate_patterns(n)
pattern = Pattern(n, cross)
filters = [Filter(n, cross, "Cross"), Filter(n, x, "X")]
del cross, x

results = [benchmark_mac_layouts(pattern, item, repeats) for item in filters]
calls = sum(item["repeats"] for item in results)
print(f"{platform.system()} {platform.machine()}, CPython {platform.python_version()}")
print(f"N={n}, 패턴=Cross, 필터=Cross/X, 조합당 반복={repeats}")
for layout, key in (("2D", "average_ms"), ("1D", "flat_average_ms")):
    average = sum(item[key] * item["repeats"] for item in results) / calls
    print(f"{layout} 호출당 평균: {average:.4f} ms (총 {calls}회)")
status = Path("/proc/self/status").read_text(encoding="utf-8").splitlines()
peak_kib = int(next(line for line in status if line.startswith("VmHWM:")).split()[1])
print(f"프로세스 최대 RSS: {peak_kib / 1024:.2f} MiB (VmHWM: {peak_kib} KiB)")
PY
```

출력 시간은 두 조합의 호출 수로 가중한 방식별 평균이다. 생성·검증·평탄화·점수 확인은 MAC 타이머 밖에서 수행한다.
`VmHWM`은 인터프리터·생성·모델 복사·평탄화를 포함한 프로세스 실행 전체의 최대 RSS이며, 앞의 22.89MiB는 8바이트 원소만 연속 저장한다고 가정한 산술적 하한이다.
CPU 부하, Python 버전과 메모리 할당 상태 등에 따라 재실행 결과는 위 실측값과 달라질 수 있다.

## 제출 문서

## 보너스 기능

- 모드 1에서 필터 A/B를 입력한 뒤 패턴 첫 줄에 `Cross` 또는 `X`를 입력하면 생성한 3×3 패턴으로 판정한다. 대소문자를 구분하지 않는다.
- 모드 3에서는 1~512 사이의 정수 N을 입력한다. Cross는 가운데 행과 열을, X는 두 대각선을 1로 채우며 나머지는 0이다. 짝수 크기의 Cross는 가운데 두 행·열 중 아래 행과 오른쪽 열을 사용한다.
- 생성한 두 패턴을 각각 두 필터와 비교한다. N=1이면 두 모양이 같아 모두 동점이다. N이 15 이하이면 두 배열을 화면에도 표시한다.
- 수동·JSON·생성 모드에서 같은 조합의 2차원 MAC과 길이 N²의 1차원 MAC을 비교한다. 측정은 조합당 각 방식 최소 10회이며, 판정과 테스트 집계는 패턴당 한 번이다.
